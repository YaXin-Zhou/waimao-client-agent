# 外贸客户智能体开发基线

版本：v0.1

状态：需求冻结前的工程基线

## 1. 项目目标

构建一个配置驱动的外贸客户开发工作流，支持：

```text
配置目标条件 → 发现潜客 → 官网背调 → 数据清洗 → 客户评分
→ 生成开发信 → 人工审核 → 阿里邮箱发送 → 读取回复
→ 回复分类 → 生成跟进建议 → 人工确认后继续跟进
```

第一阶段的成功标准是跑通一条可追溯的真实业务闭环，而不是证明可以无人值守批量开发客户。

## 2. 产品原则

1. 配置优先：产品、国家、行业、客户类型、评分权重、邮件模板、发送限制和跟进规则均通过表单或选择项管理。
2. 证据优先：AI 结论必须关联官网或其他来源，不把模型猜测当成事实。
3. 人在回路：AI 生成建议，用户确认重要业务动作。
4. 可恢复：任务、步骤、失败原因、重试次数和邮件状态必须持久化。
5. 可追溯：客户数据、评分、邮件版本和人工修改保留审计记录。
6. 小步交付：每个阶段都有明确输入、输出、测试和验收标准。

项目目录职责以 [PROJECT_STRUCTURE.md](./PROJECT_STRUCTURE.md) 为准。代码、配置、测试、文档和运行产物不得跨目录随意放置；新增一级目录必须先更新目录规范。

## 3. 已确认需求

### 3.1 业务能力

- 用户填写或选择目标客户条件。
- 系统根据条件发现目标公司和公开联系信息。
- 系统分析官网并形成结构化背调。
- 系统执行数据清洗、去重、合并和质量校验。
- 系统根据可配置评分机制对客户排序。
- 系统生成个性化开发信。
- 用户审核后通过阿里邮箱发送。
- 系统读取阿里邮箱回复并进行意向分类。
- 系统生成跟进草稿和下一步建议。
- 用户确认后发送后续邮件。
- 客户资料可以表格化查看、筛选、导出和人工修正。

### 3.2 暂不纳入第一阶段

- 自动报价、自动承诺交期或自动签署商务文件。
- 无人工审核的全自动回复。
- 复杂 CRM、销售业绩、计费和组织权限体系。
- 无限量搜索、批量发信和绕过访问限制。
- 对成交率、回复率和邮箱到达率作结果保证。

## 4. 领域模型

### 4.1 实体

| 实体 | 关键属性 | 生命周期 |
|---|---|---|
| 获客任务 | 目标条件、执行规则、状态、统计 | 草稿→运行中→暂停/完成/失败 |
| 潜客公司 | 原始名称、官网、发现来源 | 发现→待清洗→已归档或转客户档案 |
| 客户档案 | 公司、联系人、邮箱、评分、证据 | 待审核→合格/暂缓/无效/黑名单 |
| 背调报告 | 结构化字段、结论、置信度、证据 | 生成→待审核→确认/需重做 |
| 开发信 | 收件人、主题、正文、模板版本 | 草稿→待审核→已发送/取消 |
| 邮件线程 | 消息、回复、状态、分类 | 已发送→已回复/退信/无回复/暂停 |
| 跟进动作 | 下一步、执行时间、草稿、审核状态 | 建议→待审核→已执行/取消 |
| 审计事件 | 操作者、动作、对象、前后值、时间 | 追加写入，不覆盖 |

### 4.2 关键关系

```text
获客任务 1 ── N 潜客公司
潜客公司 1 ── 0..1 客户档案
客户档案 1 ── N 背调报告
客户档案 1 ── N 开发信
客户档案 1 ── N 邮件线程
邮件线程 1 ── N 跟进动作
所有实体 1 ── N 审计事件
```

## 6. 工作流状态标准

### 6.1 任务状态

`草稿 → 待运行 → 运行中 → 等待审核 → 运行中 → 已完成`

异常分支：`运行中 → 暂停`、`运行中 → 失败`、`失败 → 重试`。

### 6.2 客户状态

`新发现 → 清洗中 → 待评分 → 待审核 → 已入选 → 已联系 → 已回复 → 跟进中 → 已转化/暂缓/无效`。

### 6.3 邮件状态

`草稿 → 待审核 → 已批准 → 发送中 → 已发送 → 已回复`。

异常状态：`退信`、`发送失败`、`取消`、`暂停跟进`。

状态变更必须记录操作者、时间、原因和关联任务。

## 7. 数据清洗规则

清洗中心必须输出“原始值、标准值、处理动作、置信度、来源”。

- 公司名：去除无意义符号，统一大小写和空格，保留原始名称。
- 官网：补全协议，提取主域名，识别重定向和无效链接。
- 邮箱：格式校验，域名提取，标记公共邮箱和疑似个人工作邮箱。
- 公司去重：优先按主域名，其次按邮箱域名、公司名相似度和国家组合判断。
- 结果合并：多条搜索结果合并为一条客户档案，保留全部来源。
- 质量标记：完整、部分完整、冲突、疑似错误、待人工核验。
- 黑名单：用户可以按公司、域名、邮箱加入黑名单，后续任务跳过。
- AI 背调：没有证据的字段不自动补全，统一写为“未知”。

## 8. 安全回复策略

以下内容只生成草稿，不自动发送：报价、交期、付款条件、合同、投诉、敏感信息、低置信度分类和客户明确要求人工联系的内容。

自动化可以做：同步收件箱、识别回复线程、分类客户意向、提取客户问题、生成回复建议、安排待办。

发信前必须检查：收件人、主题、正文、附件、重复发送、黑名单、发送额度、最近联系时间和审核人。

## 9. 分阶段开发计划

### Phase 0：需求冻结和领域建模

输出：需求基线、术语表、状态机、验收样例、未决问题清单。

验收：核心名词无歧义，首条完整业务闭环有明确输入和输出。

### Phase 1：配置与任务骨架

输出：目标条件表单、配置持久化、任务创建、任务状态和审计事件。

验收：用户不改代码即可创建不同产品、国家和客户类型的任务。

### Phase 2：客户发现与数据清洗

输出：搜索结果接入、官网信息采集、客户档案、清洗、去重、来源记录。

验收：同一公司多来源结果可以合并，错误字段可人工修正。

### Phase 3：背调与评分

输出：结构化背调、证据关联、评分项配置、客户排序和人工复核。

验收：每个评分结果有明细，无法证明的结论不会被当作事实。

### Phase 4：开发信与人工审核

输出：邮件模板、个性化变量、开发信草稿、审核队列和版本记录。

验收：用户可以修改、退回、批准或取消每封邮件。

### Phase 5：阿里邮箱和回复跟进

输出：SMTP 发信、IMAP 收信、线程关联、回复分类、跟进草稿。

验收：真实邮箱完成一次发送、收信、分类和人工确认跟进。

### Phase 6：真实业务验收与交付

输出：部署说明、备份恢复说明、操作手册、验收报告和遗留问题。

验收：使用客户真实产品和真实邮箱跑通完整闭环，并由客户确认结果。

## 10. 工程规范

每个功能必须先补充：需求编号、业务规则、输入输出、异常场景、权限边界和验收标准。

每个开发任务必须经过：

```text
需求卡片 → 设计说明 → 实现 → 单元测试 → 集成测试
→ 真实界面验证 → 代码审查 → 更新文档 → 验收记录
```

禁止直接在聊天中临时追加功能并立即修改代码。新增需求必须进入变更记录，标注影响范围、优先级、风险和是否影响当前验收基线。

## 11. 测试金字塔

- 单元测试：清洗规则、去重、评分、状态转换、模板变量。
- 集成测试：任务编排、数据库、搜索适配器、AI 适配器、邮箱适配器。
- UI 测试：创建任务、审核客户、审核邮件、查看回复、执行跟进。
- 真实验收：真实官网、真实邮箱、真实回复和客户指定样例。
- 安全测试：重复发送、黑名单、退信、失败重试、权限、敏感内容拦截。

Fake 数据只能验证流程逻辑，不能替代真实网页、真实模型、真实邮箱和客户验收。

## 12. 变更控制

所有新需求进入 `CHANGELOG.md` 或需求登记表，至少记录：

- 需求编号和提出人；
- 业务目的；
- 优先级：P0 / P1 / P2；
- 影响模块；
- 对数据模型、状态机和验收标准的影响；
- 是否纳入当前阶段；
- 验证结果和最终决定。

没有验收标准的需求不得进入开发完成状态。

## 13. 当前工程完成定义

一个阶段只有同时满足以下条件才能标记完成：

- 需求和验收标准已确认；
- 代码、配置和数据模型已实现；
- 自动化测试通过；
- 关键流程经过真实界面验证；
- 失败和恢复路径已验证；
- 文档和操作说明已更新；
- Git diff、提交记录和遗留问题清晰；
- 阶段验收结果有证据。

“服务能启动”“接口返回成功”“Fake 测试通过”不能单独代表业务完成。

## 14. 首批必须确认的业务问题

1. 产品资料和目标客户画像由谁维护？
2. 评分项和权重是否允许销售人员修改？
3. 每次任务最多处理多少家公司？
4. 哪些邮箱可以发送，哪些邮箱需要排除？
5. 哪些回复允许自动生成草稿，哪些必须升级人工？
6. 客户档案保留多久，谁可以查看和修改？
7. 最终表格需要哪些固定列？
8. 第一条真实验收样例是什么？
