- **检查范围**：真实官网背调、联系人证据、客户评分、DeepSeek 开发信草稿、中文预览、人工审核、发件人资料、前端工作台

## 2. 总体结论

当前项目已经形成了一个可运行的核心纵向切片：

```text
真实官网
  ↓
官网背调与来源证据
  ↓
联系人邮箱补充与证据绑定
  ↓
真实 DeepSeek 生成英文开发信草稿
  ↓
中文机器翻译预览
  ↓
人工审核状态
```

这条链路适合作为 MVP 的基础，但目前仍属于“可验证原型”，不是可以直接交给客户长期运行的生产系统。下一阶段应优先补齐数据真实性边界、任务和状态模型、审计记录及邮箱接入前的安全检查，而不是继续堆叠页面功能。

## 3. 已经做得比较好的部分

### 3.1 真实数据边界已经建立

- 真实搜索结果和真实官网内容会进入持久化客户档案。
- 没有证据的行业、公司规模等字段显示为“未知”，不会擅自写成确定事实。
- 联系人邮箱必须附带来源 URL 和来源说明才能保存。
- 开发信生成要求真实邮箱和真实背调存在。
- 真实样本 `Solar-Generatoren.de` 当前使用官网公开邮箱 `kontakt@solar-generatoren.de`，并保留官网来源。

### 3.2 人工审核边界清晰

- DeepSeek 只生成草稿，不发送邮件。
- 草稿状态可以进入批准或退回修改。
- 中文翻译仅为阅读预览，不覆盖英文原文。
- 发件人资料独立配置，生成新版本不会覆盖旧草稿。

### 3.3 工程基础可维护

- 领域、应用、基础设施、接口和前端目录已经分开。
- SQLite 持久化、服务层和 HTTP 适配器之间有基本边界。
- 当前自动化检查为 `65 passed`，Ruff、Python 编译和 Vite 构建均通过。
- 已建立私有 GitHub 仓库并持续提交。

## 4. 当前问题与风险

优先级定义：

- **P0**：进入真实客户试用前必须处理
- **P1**：核心闭环扩展前应处理
- **P2**：规模化或体验优化阶段处理

### P0-1：前端仍存在演示数据回退

**证据**：API 请求失败时前端将 `apiState` 设置为 `demo`，并回退到本地 `leads`；首页统计还存在固定的 `12`、`28`、`37` 等演示值，开发信组件也保留非远程客户的示例正文。

**风险**：本地 API 中断、任务为空或接口异常时，用户可能误以为看到的客户和指标是真实数据。这正是之前出现“公司规模推测”和“测试数据真假混淆”的根源之一。

**建议**：

1. 增加明确的“演示模式”开关，默认关闭。
2. 真实模式下接口失败只显示错误状态，不展示示例客户。
3. 每个统计指标标明数据来源和统计时间；接口未接入时显示“未接入”，不能显示模拟数字。
4. 在页面顶部持续显示“真实数据 / 演示数据”状态。

### P0-2：任务选择模型不完整

**证据**：当前前端加载任务列表后只使用第一个任务，没有任务切换器；客户、草稿和发件人资料均围绕当前任务工作。

**风险**：多个产品、国家或销售人员同时使用时，用户无法确认当前客户属于哪个任务，容易在错误任务下生成草稿或修改发件人资料。

**建议**：下一阶段实现任务选择器，并在页面标题、客户列表和所有写操作中显示任务名称与任务 ID。没有明确选择任务时禁止生成草稿和修改配置。

### P0-3：审核操作界面存在重复入口

**证据**：开发信区域同时存在草稿卡片上的“批准草稿 / 退回修改”按钮，以及下方“审核操作”区域的同名按钮。上方部分按钮仍只是本地提示，真正调用审核接口的是下方区域。

**风险**：用户会误以为点击上方按钮已经完成审核，造成界面反馈与真实状态不一致。

**建议**：保留一个真实接入审核接口的操作区，删除或明确标记另一组旧按钮；所有状态变化都应等待接口成功后再更新页面。

### P1-1：客户状态和邮件状态尚未形成完整状态机

**证据**：文档已经定义了客户、邮件和任务状态，但当前实现主要覆盖草稿和审核，尚未覆盖发送、回复、退信、暂停跟进、失败重试等状态。

**风险**：后续接入阿里邮箱时容易直接把“批准”当作“已发送”，或者用字符串临时拼接状态，导致跟进逻辑不可审计。

**建议**：先实现领域层状态转换、非法转换测试和状态变更事件，再接邮箱适配器。状态转换必须记录操作者、时间、原因和关联对象。

### P1-2：审计记录和权限边界不足

**风险**：当前审核人由表单输入，尚未形成真实用户身份；谁修改了联系人、谁批准了草稿、谁改变了发件人资料，缺少可靠审计链。

**建议**：在单用户本地版至少建立操作者配置和审计事件表；进入多人或客户部署前再接登录、角色、权限和密钥隔离。API Key 只能从环境变量读取，不能写入数据库、日志或前端。

### P1-3：搜索、抓取和模型调用缺少后台任务边界

**风险**：真实网站访问、搜索 API、DeepSeek 调用和翻译服务都可能超时或限流。如果请求直接占用 HTTP 连接，页面刷新或网络抖动可能造成重复任务、重复草稿或状态丢失。

**建议**：引入持久化任务表和任务执行记录，至少支持排队、运行中、成功、失败、重试和取消；外部调用增加超时、重试上限、幂等键和原始响应摘要。

### P1-4：中文翻译服务不是完全离线能力

**证据**：当前非大模型翻译依赖第三方网页接口；项目文档已经记录该服务依赖外网，Argos Translate 仅作为未来离线替代方案。

**风险**：邮件内容可能离开本机，服务稳定性和隐私边界不由本项目控制。

**建议**：MVP 可保留当前方案，但界面应显示“第三方机器翻译预览”；客户部署前评估 Argos Translate 或其他本地翻译引擎，并增加术语表和翻译质量抽检。

### P2-1：评分和数据清洗仍需更多真实样本验证

当前评分机制已支持配置权重，方向正确；但真实样本数量很少，尚不能证明行业、国家、客户类型和来源冲突场景下的评分稳定性。

建议积累一组人工标注样本，比较“规则分数、人工判断、最终转化结果”，再调整权重。任何推测字段都必须保留推测标签、来源和置信度，不能混入确定事实。

### P2-2：可观测性和备份恢复尚未达到交付要求

正式运行前还需要：结构化日志、任务耗时、外部调用错误统计、SQLite 自动备份、恢复演练和敏感字段脱敏。仅有 `/api/health` 不能代表业务链路可用。

## 5. 当前未验证的内容

以下内容不能因为单元测试通过而视为已完成：

- Google 或其他搜索源的大规模真实搜索稳定性。
- 多网站抓取、超时、重定向、验证码和限流场景。
- 大规模真实 DeepSeek 调用的成本、延迟和输出一致性。
- 阿里邮箱 SMTP 发信和 IMAP 收信。
- 真实回复线程关联、退信识别和自动跟进。
- 多用户权限、密钥保护、黑名单和发送额度控制。
- 客户最终验收。

## 6. 推荐整改顺序

### 下一阶段：任务上下文与真实模式隔离

**目标**：让用户始终知道当前操作针对哪个真实任务，并彻底避免接口异常时混入演示数据。

**交付物**：

1. 任务选择器和任务上下文栏。
2. 真实模式 / 演示模式显式开关。
3. API 失败、空任务和无数据状态页。
4. 移除或隔离固定统计值和示例开发信。
5. 任务上下文相关的接口和前端测试。

**验证重点**：切换任务后客户、联系人、草稿和发件人资料不串数据；关闭 API 后页面不会显示伪造客户。

### 再下一阶段：状态机与审计

**目标**：把客户、草稿和后续跟进变成可追踪的业务对象。

**交付物**：状态转换模型、审计事件、非法转换测试、审核入口合并、失败重试记录。

**验证重点**：每次状态变化都有操作者、时间、原因和前后状态；批准不等于发送。

### 邮箱阶段：先收件再发送

**目标**：建立阿里邮箱连接、收件箱同步、线程关联和回复分类，但继续保持人工确认边界。

**交付物**：邮箱配置、连接测试、收件同步、线程模型、退信识别、跟进建议草稿。

**验证重点**：先用专门测试邮箱验证收信和回复分类；发送功能单独经过安全检查、人工确认和客户授权后再验收。

## 7. 结论

项目目前的方向是正确的，最重要的“真实证据优先”和“生成不等于发送”已经落地。现在最大的隐患不是模型能力，而是产品状态和数据边界：必须先让系统在异常、空数据、多任务和审核操作下仍然诚实、可追踪、不可误操作，再进入邮箱自动化。
